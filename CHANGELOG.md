# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **True S3-native mode: durable-without-local-state.** Object storage is the source of truth in cloud mode. On cold start, a node with an EMPTY local disk discovers its collections from S3 (`list_namespaces`) and **rebuilds all local indexes** (redb/Tantivy/HNSW/filter-index) by materializing the manifest — reading compacted segments + replaying uncompacted WAL fragments (latest-wins, deletes applied). This covers **chunks, the parent/group hierarchy, AND typed many-to-many relations** — relation create/delete are mirrored into the WAL (`relation_upsert` / `relation_delete` fragments) and reconstructed on recovery. An ephemeral container that loses its local disk recovers every collection from the bucket. Verified end-to-end against MinIO (destroyed the container + its local volume, brought up a fresh one, data — minus a deleted chunk, plus surviving relations — came back).
- **Compaction that reclaims deleted data — manual + automatic.** `POST /collections/:name/compact` folds all segments + WAL fragments into ONE new UUID-keyed segment (applying tombstones), physically removing deleted records so they can never resurrect. Compaction also runs **automatically in the background** once a collection's uncompacted WAL exceeds a fragment threshold (off the write path), so deletes reclaim space without operator action.

### Scope & limitations (honest)

- **Reads are served from local indexes, not directly from S3.** Cloud mode is "durable via S3, fast via local": every node rebuilds local indexes from S3 on start and serves from them. It is NOT stateless multi-node serving — each node needs local disk for its rebuilt indexes, and two nodes do not share a live view. Truly stateless serving from S3 (HNSW/BM25 over object storage) is future work.
- **Recovery materializes the whole live set into RAM.** `materialize` builds the full chunk+relation set in memory, so cold-start recovery of a very large collection is bounded by RAM (not yet streaming/out-of-core). The engine remains single-node.

### Fixed

- **Torn mmap append no longer corrupts vector files (critical).** A crash between a vector-file data write and its header count update leaves orphan bytes past the logical end; appends now write at the logical end computed from the trusted header (overwriting any orphan tail) instead of physical EOF, data is synced before the count is bumped, and a corrupt header can no longer overflow the open-time size check.
- **Embedding dims are validated on ingest (critical).** A single wrong-length embedding from an API caller used to silently corrupt the vector file in release builds (validation was `debug_assert`-only). Ingest now rejects mismatched embeddings with a 4xx before anything is written, the mmap layer enforces dims as a hard error, and loading a vector file whose on-disk dims disagree with the collection config fails loudly instead of returning garbage scores.
- **No chunk-id reuse after compaction (high).** Compaction physically drops tombstoned chunks; the segment now stores the id high-water mark (`max_id`) so a cold rebuild can't recompute `next_id` from live chunks only and hand deleted ids to new data. Also fixes the off-by-one that reused the highest id when every chunk was deleted. Regression-tested (compact → cold restart → fresh ingest takes a fresh id).
- **GCS conditional writes work (high).** The CAS version token now carries both the HTTP ETag and the provider version (the GCS object *generation* — GCS requires it and ignores the ETag). Previously every `gs://` manifest commit after the first failed with "Missing Version".
- **`s3://bucket/prefix` is honored (high).** A path after the bucket now scopes all keys via `PrefixStore`; previously the prefix was silently dropped, so two deployments configured with different prefixes in one bucket clobbered each other's data.
- **Duplicate ids in one delete request no longer corrupt `chunk_count`.** `{"ids":[5,5,5]}` counted (and decremented the persisted live count by) three; ids are now deduped.
- **Deleted chunks report `target_status: "missing"`.** All relation reads (create, list, search enrichment) now consult tombstones; deleted chunks were reported `"found"`. The filter index also excludes tombstoned ids on every load path, so selectivity/`eligible` no longer count deleted chunks (which could underfill top-k on deleted-heavy collections).
- **Mid-ingest index failure no longer disables a vector space.** An error during the incremental HNSW update used to drop the whole vector space from RAM (silent semantic-search outage until restart) and could desync the vector file from its keymap on disk (search then fabricated chunk ids). The space is now always restored and the keymap is persisted in step with the vector file.
- **Ingest/relation compensation on partial failure.** If the local commit fails after the durable S3 append (or the collection is deleted mid-flight), ingest now tombstones the batch in local redb + RAM + S3 (so it can't resurrect via ANY restart path, including persistent-disk reloads that skip cloud recovery), and relation-create appends a compensating relation-delete. Compensation failures are logged loudly instead of swallowed.
- **v1→v2 vector-file migration streams** (raw byte copy) instead of materializing every vector in RAM.
- **Storage/API hygiene.** Local CAS shard locks now also cover plain `put`/`put_if_not_exists` (no in-process lost updates); local `NotFound` errors carry the logical key, not the server filesystem path; 500 bodies no longer leak internal error details (logged server-side instead); relation batches are capped per request; empty `?types=` means "all", not "none"; `.env.example` is no longer swallowed by `.gitignore`; the startup probe leaves no residue; embedding-model loaders degrade gracefully on non-UTF-8 paths instead of panicking.
- **Namespace discovery is O(namespaces), not O(objects).** The `Storage` trait gained a delimiter-listing primitive (`list_dirs`, native `list_with_delimiter` on object stores, one readdir locally); cloud boot no longer enumerates every WAL fragment/segment in the bucket just to find manifests.
- **Relation endpoint indexes are redb multimaps.** Inserting/removing an edge touches one index entry instead of decode-append-rewriting a per-chunk id blob — a hub chunk with N edges costs O(N log N) to build, not O(N²). Upserting a relation_id with changed endpoints prunes its stale index entries.
- **Real-S3 integration tests.** Env-gated tests (skip cleanly when `COMPASS_TEST_S3_BUCKET` is unset) exercise genuine server-side ETag CAS, the full LSM lifecycle with physical GC, and concurrent appends against a real S3-compatible endpoint — verified against MinIO. See `storage/s3_integration_tests.rs` for the run recipe.
- **Compaction now GCs old objects — no unbounded storage leak (critical).** The production compaction path (`replace_with_single_segment`) staged old segments+fragments for deletion but never actually deleted them, leaking every prior object (and bloating the manifest) on every cycle. It now physically GCs the prior cycle's staged objects after a successful CAS commit (deferred one cycle for in-flight readers), and deletes the just-written segment on CAS conflict so lost/racing compactions don't orphan a full segment. Object count is regression-tested to stay bounded across many compaction cycles.
- **Auto-compaction is single-flighted.** Concurrent background compaction triggers for the same collection could each write (and, on CAS loss, leak) a full segment; now only one runs per collection at a time.
- **`delete_collection` purges object storage.** A deleted collection's objects are removed from S3, so it can't be resurrected on a later cold start (and a racing ingest's orphan fragment can't bring a "deleted" collection back).
- **Global write-lock no longer held across S3 network I/O.** `ingest`, `delete_chunks`, `create_relations`, and `delete_relation` now release the collections lock before the S3 round-trip (compute under lock → drop → S3 → reacquire to apply), so a slow/hung S3 endpoint no longer stalls every other collection's reads and writes. Regression-tested with concurrent ingests (all durable, ids unique).
- **Concurrent-append data loss (critical).** WAL fragments are now keyed by a unique UUID, not by `next_seq`. The old scheme let two racing appenders pick the same seq and overwrite each other's fragment object; the losing writer's data was silently lost. Fragment objects are now written at unique keys and only the manifest ref (with its seq assigned at CAS-commit time) is contended. Regression-tested with 16 concurrent appends.
- **Delete / ingest local↔S3 split-brain (critical).** In cloud mode the durable S3 WAL append now happens BEFORE any local commit. Previously local state committed first, so a failed S3 mirror left the batch/delete applied locally while a retry (seeing the id already handled) never wrote the durable record — data diverged and deleted chunks resurrected on rebuild. On S3-append failure the in-RAM mutations are now rolled back and the caller can retry cleanly.
- **Chunk-id reuse after soft-delete (high).** `next_id` is now a persisted monotonic high-water mark, never decremented by delete — so a cold restart with an empty local chunk store can't reuse an already-assigned id and overwrite existing chunks. (Previously it fell back to the live `chunk_count`, which delete decrements.)
- **`put_if_not_exists` is now a true create primitive.** `LocalDiskStorage` uses `OpenOptions::create_new` (atomic O_EXCL) instead of a racy `exists()`-then-rename that could overwrite a concurrently-created file — so the manifest first-write / lease-acquisition contract holds across processes.
- **CAS with an empty ETag is refused** rather than silently matching any object with a missing ETag (which could corrupt the manifest-commit guarantee).
- **Relation pruning on chunk delete now propagates errors** instead of swallowing them, so a failed prune can't silently leave edges dangling at a deleted chunk.
- **`ChunkCache::get_batch` honors its documented ordering contract** (returns chunks in request-id order, not hits-then-misses).

- **Delete (soft-delete) — local and S3-native.** New `DELETE /collections/:name/chunks/:id` and `POST /collections/:name/delete` ({ids, filters}) soft-delete chunks by id or metadata filter. Deletes are tombstones: the chunk vanishes from search/facets/segments immediately (filtered by an in-RAM id set, persisted to a redb `tombstones` table so it survives restart); physical removal from the HNSW/FTS indexes happens on the next rebuild/compaction. In object-storage mode a durable **tombstone WAL fragment** (`kind: "tombstone"`) is appended to the LSM, so the deletion is S3-native. Incident relations are pruned. Verified end-to-end against MinIO: delete-by-id and delete-by-filter each wrote a tombstone fragment, and search correctly excluded the deleted ids.
- **LSM compaction data-loss fix + tombstone support.** Compaction now uses a *strict* fragment read that **aborts if any listed WAL fragment is missing**, instead of silently skipping it and advancing the watermark past un-merged data (a latent data-loss bug). Fragments carry a `kind` (`data` | `tombstone`); tombstones are recorded in the manifest and honored by compaction.

- **Storage abstraction (`Storage` trait) + object-storage backend.** New `storage/` module introducing a source-of-truth `Storage` trait — object-keyed, byte-range-readable (`get_range`), and CAS-capable (`put_if_match` / `put_if_not_exists`). Two backends: `LocalDiskStorage` (default; the existing local-first embedded behavior, zero change) and an opt-in `ObjectStoreBackend` over the `object_store` crate covering **S3 / GCS / Azure / R2 / MinIO / in-memory** in one dependency. Selected via `COMPASS_STORAGE` (`local` default, or `s3://…` / `gs://…` / `az://…`); a hard either/or. The object backend is behind a non-default `object-storage` cargo feature so local builds stay lean. Local-first remains the default and is never required to opt in.
- **LSM persistence layer (WAL + manifest + compaction).** New `storage/lsm.rs` — the object-storage answer to "do everything redb does, but in object storage" (redb can't run on object storage). Immutable WAL fragment objects written first for durability, a CAS-committed manifest as the single source of truth, and background compaction folding fragments into segments with deferred GC. Generic over any `Storage` backend, so the identical code path runs on local disk or object storage. Follows the WAL-fragment + CAS-manifest design proven by object-storage-native databases.
- **Object-storage mode wired end-to-end (ingest → S3-native WAL).** `CollectionManager` now takes a `Storage` backend (`new_with_storage`), selected at startup from `COMPASS_STORAGE`. In object-storage mode, every ingest batch is mirrored into the LSM as an immutable WAL fragment (`{collection}/wal/{seq}.frag`) plus a CAS-committed `{collection}/manifest` — so ingested data is durably S3-native. Local mode is unchanged (no LSM objects written). Startup runs a connectivity check (put/get/delete round-trip) so bad credentials/bucket/region fail loudly at boot. New `.env.example` documents S3/GCS/Azure credentials; `docker-compose.minio.yml` provides a runnable MinIO stack to watch the objects appear. Verified end-to-end against MinIO: two ingest batches produced two WAL fragments + one manifest in the bucket. **Note:** search still reads from the local indexes; serving queries from object-storage segments (compaction on the live path) is the next increment.
- **Out-of-core building blocks.** New `ChunkCache` (`search/chunk_cache.rs`): a bounded LRU read-through over the disk-backed `ChunkStore`, so large collections no longer require rehydrating every chunk into an unbounded in-memory map. `FilterIndex` gains `serialize` / `deserialize` (native roaring-treemap format + a versioned container) so the filter index can be persisted and reloaded instead of rebuilt from all chunks on every restart/ingest.

- **Typed, many-to-many chunk relations.** New directed labeled edges between chunks (`source --relation_type--> target`), independent of the parent/group hierarchy. New `RelationStore` (`collections/relation_store.rs`), redb-backed and disk-served (read on demand, never resident in RAM), with `relations` + `by_source` + `by_target` tables. Endpoints: `POST /collections/:name/relations` (batch create, server-minted UUIDv4 ids), `DELETE /collections/:name/relations/:relation_id`, `GET /collections/:name/chunks/:chunk_id/relations` (with `direction` = outgoing/incoming/both and `types` filters). Search gains opt-in `include_relations` / `relation_types` / `relation_direction`; each `SearchHit` then carries a `relations` field (absent unless requested). Self-relations are rejected; `target_status` (found/missing) is resolved at read time.

- **Memory-mapped vector storage.** New `MmapVectors` module (`search/mmap_vectors.rs`) replaces `Vec<Vec<f32>>` with a flat mmap-backed file. Zero-copy reads via `bytemuck::cast_slice`, append-only writes, near-zero RSS for vector data regardless of dataset size. File format: `[u32 dims][u32 count][f32...]`.
- **Disk-backed chunk metadata.** New `ChunkStore` module (`search/chunk_store.rs`) backed by redb (pure Rust embedded DB). Replaces in-memory `HashMap<u64, DocumentChunk>` with persistent, ACID-compliant storage. Point lookups, batch inserts, full scans for rebuild.
- **Incremental HNSW indexing.** Ingest path now loads the existing USearch index via `.load()`, appends new vectors with `.add()`, and saves — instead of cloning all vectors and rebuilding from scratch. Falls back to full rebuild when the `Arc` cannot be unwrapped.
- **New dependencies:** `memmap2` (mmap), `bytemuck` (zero-copy cast), `redb` (embedded DB).
- **Cargo workspace layout.** Source moved from a single crate to a workspace under `crates/`. Splits: `compass` (umbrella + binary), `compass-index-api` (stable trait surface), `compass-vector-gpu` (optional GPU backend).
- **Vector index trait abstraction.** New `compass_index_api::VectorIndex` trait abstracts over CPU and GPU backends. The existing USearch path is wrapped in `UsearchHnswIndex`; new backends bind to the trait without touching call sites.
- **Optional GPU backend (`--features gpu`).** New `compass-vector-gpu` crate integrates NVIDIA cuVS for CAGRA→HNSW build acceleration. CPU-side search after conversion. Linux + CUDA 12+ only. See `ARCHITECTURE.md` for build prerequisites.
- **`COMPASS_BACKEND` env var.** Selects the vector backend at startup: `cpu` (default), `gpu`, `auto`.
- **`ARCHITECTURE.md`.** Contributor's map: crate layout, module map, storage format, rebuild flow.
- **`CONTRIBUTING.md`.** PR checklist, commit format, scope guidelines.
- **Throughput and scaling section** in README documenting QPS expectations and horizontal scaling pattern.
- **Rich metadata filters.** Filters now support numeric range (`gte`/`lte`), array `contains`, and set membership (`in`) in addition to exact match. Backward compatible: plain values still work as exact match.
- **TAMS time-range queries.** Filter segments by `timerange_start`/`timerange_end` using range operators. Combined with `doc_type` filtering and relationship boost for hierarchy-aware video search.
- **Parent metadata on segment search hits.** Search responses now include `parent_metadata` on each `SearchHit` whose chunk is a segment with a `parent_id`. Saves the agent a second round trip to fetch source-level attributes (asset title, fps, duration, etc.). Parents are deduplicated across hits: N segments sharing the same parent pay for one lookup, not N. Non-segment hits and segments without a `parent_id` carry no `parent_metadata` field in the JSON response.
- **Temporal segment lookup.** New `GET /collections/:name/segments/at` endpoint returns `doc_type=segment` chunks matching a point in time (`time`) or overlapping a time window (`time_start`/`time_end`), filtered by `group_id` (`asset` param). Results sorted ascending by `timerange_start`. Full-scan implementation; indexed lookup by `group_id` is tracked as future work.
- **Configurable hybrid score weights.** New `score_weights` field on search requests controls RRF blending: `rrf_k`, `fts_weight`, `semantic_weight`. Previously hardcoded at k=60 with equal weights.
- **Recency presets.** `recency_preset` field accepts `aggressive` (3d), `recent` (7d), `mild` (30d), or `archive` (90d) instead of manually configuring the decay formula. Pair with `recency_field` to specify which timestamp metadata field to use.

### Changed

- **Cargo manifest** is now a workspace root with shared `[workspace.dependencies]` and `[workspace.package]` metadata. Per-crate manifests inherit version, edition, and rust-version.
- **Compiler profile** adds `lto = "thin"` and `codegen-units = 1` to release builds for better optimization. Adds debug symbols to bench builds.
- **MSRV bumped to 1.88** from 1.82. Required by `time@0.3.47` (edition 2024) and `icu_collections@2.2.0`.
- **Dockerfile** upgraded to `rust:latest` + `debian:trixie-slim` for glibc compatibility with newer Rust toolchains.

### Deprecated

- Direct use of `compass::search::vector` from external code. New code should bind to `compass::search::VectorIndex`. The legacy `vector.rs` functions remain for in-tree callers and will be wrapped or migrated incrementally.
- **`timerange_start` / `timerange_end` (in seconds).** Renamed to `timerange_start_ms` / `timerange_end_ms` (in integer milliseconds) so the unit is visible in the field name and matches the convention used by real-world sidecar producers (which commonly emit milliseconds). Existing data ingested against the old field names should be renamed and multiplied by 1000 in the transform.

### Changed (breaking)

- **`GET /collections/:name/segments/at` query parameters renamed.** `time` → `time_ms`, `time_start` → `time_start_ms`, `time_end` → `time_end_ms`. All values are now integer milliseconds rather than seconds. Matches the standard sidecar field convention.
- **Time-range field convention is now milliseconds.** Segment metadata uses `timerange_start_ms` and `timerange_end_ms` as numeric (integer) milliseconds. The `/segments/at` endpoint and `segment_in_time_window` predicate look up the new field names. Instants (zero-duration events such as instantaneous markers from sidecars) are stored as segments where `timerange_start_ms == timerange_end_ms`; the point query at that exact ms matches them, as do range queries that overlap.

### Fixed

- **Filter index covers the full `u64` chunk-id space.** The roaring filter index keyed chunk ids as `u32` and silently dropped any chunk with `id > u32::MAX` at insert (and treated it as ineligible at query), so filtered search could never return those chunks. Switched `FilterIndex` from `RoaringBitmap` to `RoaringTreemap` (64-bit); the overflow guard and `as u32` casts are gone. No chunk is dropped regardless of id magnitude.
- **mmap vector file no longer corrupts past 4.29B vectors.** `MmapVectors` stored its vector count as a `u32` header field (`vectors.len() as u32`), which silently wrapped past `u32::MAX` and corrupted every subsequent read offset. The header is now a versioned v2 layout (`magic + u32 dims + u64 count`); legacy v1 files are read transparently and migrated to v2 on the next append.
- **ChunkStore tolerates stale `flock` state on networked filesystems.** redb acquires an exclusive `flock(LOCK_EX | LOCK_NB)` on the database file at open. On network-backed persistent volumes (NFS and similar), the kernel does not always release a previous process's `flock` immediately after that process exits. A restarted process then sees `DatabaseError::DatabaseAlreadyOpen` and `load_collection` would silently log-and-skip the affected collection, leaving the API reporting it as missing despite the data being durable on disk. `ChunkStore::open` now retries up to 6 times with 5s backoff before giving up, and enables redb's `set_repair_callback` so any dirty-file state from a previous abrupt shutdown auto-recovers.
- **Chunk metadata is now durable across restarts.** Wired the existing `ChunkStore` (redb) into the `CollectionManager` lifecycle. Every ingest writes chunks through to `<data_dir>/<collection>/chunks.redb` in a batched atomic transaction, and `load_collection` rehydrates `loaded.chunks` from that database on startup. `next_id` is recomputed as `max(seen_id) + 1` so post-restart ingests pick up where they left off. Before this fix, chunks lived only in an in-memory `HashMap` that was initialized empty on every restart, which meant process restarts and crashes silently destroyed ingested data even when the persistent volume was correctly mounted.
- **Data directory honors `DATA_DIR`.** Ensure the engine writes indexes to the configured `DATA_DIR` persistent path rather than the container's ephemeral writable layer, so data survives restarts when a persistent volume is mounted.

## [0.1.0] - 2026-04-25

### Added

- Initial release as Captain's embedded search engine.
- Tantivy BM25 full-text search with bitset-faceted metadata.
- USearch HNSW vector search (mmap-backed, disk-persistent).
- Reciprocal Rank Fusion hybrid search.
- Named vector spaces — multiple embedding models per collection.
- One-click model upgrades with background re-embedding and atomic swap.
- Parent-child relationships with TAMS-compatible hierarchies.
- Query-time scoring: recency decay, metadata boost, relationship boost.
- Native query embedding via Candle BGE-small.
- External GPU embedding endpoint support.
